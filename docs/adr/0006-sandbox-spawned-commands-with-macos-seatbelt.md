# Sandbox spawned commands with macOS Seatbelt

Froe will keep its parent process, credentials, run state, approval UI, recorder, and OpenAI connection outside the command sandbox. Every child command, including the `rg` search helper, crosses a `CommandSandbox` seam. On macOS the production adapter generates an in-memory Seatbelt profile that denies network access, permits writes only beneath the canonical workspace and temporary directory, and limits reads to those directories, system runtime locations, and the resolved Node or pnpm toolchain. The child receives the temporary directory as `HOME` so normal home-relative credential paths are unavailable.

Ordinary commands run in the base profile without prior approval. Known destructive commands remain approval-gated. When the kernel reports a denied operation, Froe correlates it using a per-execution profile marker and proposes a one-shot exception derived from the reported capability: an exact filesystem path, or a specific network operation filtered to its logged local or remote endpoint. The action runtime retries only after explicit approval and fails closed when it cannot construct or monitor a narrow exception. Blanket approval modes never cover sandbox exceptions.

This decision supersedes ADR 0002. It accepts a macOS-specific implementation and the risk of relying on the deprecated `sandbox-exec` command and Apple's undocumented Seatbelt profile language. App Sandbox is not an equivalent replacement because it constrains a signed application rather than applying a generated profile to an arbitrary CLI child. Non-macOS command execution therefore fails closed until another real adapter exists. The interface isolates this platform dependency so the run loop, provider, and action semantics do not learn Seatbelt details.
